# hal-service-api-finder 封装判定简化设计

- 日期：2026-10-23
- 状态：设计已确认，待实现
- 目标文件：`hal-service-api-finder/SKILL.md`

## 1. 背景与目标

当前封装判定有 6 条规则（自身不处理 data、函数体简单、下游数量、dispatcher、定义唯一、名字相近），过于复杂。

新规则只保留名字与路径判断：

- 对 `<target_path>` 下接收 data、且不是 dispatcher 的业务函数，按 data 下游目标判断；
- 同一目标被调用多次只算一个目标；
- 不同目标数为 0 或 ≥2 → 当前函数为接口；
- 只有一个不同目标时：目标必须在 `<target_path>` 和 scope 内；名称相同或前后缀扩展 ≤8 字符 → 封装，否则当前函数为接口；
- 唯一目标是 dispatcher/转发器 → 按现有 dispatch 规则处理，不记录当前函数；
- 不再检查函数体复杂度、data 是否被处理、下游调用次数或纯校验调用。

## 3. 3.6 封装判定新规则

仅对 `<target_path>` 下接收 data/data 派生参数、不构成分发、且不是排除项的业务函数执行：

```text
封装判定：

1. 找出函数体内所有“实参含 data 或 data 派生值”的调用，按目标定义 `(file, line)` 去重；同一目标被调用多次只算一个目标。
2. 不同目标数为 0 → 当前函数记为接口。
3. 不同目标数 ≥ 2 → 当前函数记为接口。
4. 只有一个不同目标时：
   - 目标定义不在 `<target_path>` 或不在 scope 内 → 当前函数记为接口；
   - 目标是 dispatcher/转发器 → 不按封装处理，当前函数不记录，按现有 dispatch 规则入队该目标（`current_cmd_expr` 取调用点 cmdId 实参，`parent_case_id = origin_case_id`）；若当前已有 `fallback_handler`，按 3.9 现有 dispatcher 规则处理；
   - 目标是普通业务函数：去掉命名空间/类限定后比较名称。名称完全相同，或一个是另一个的前缀/后缀扩展且多出的部分不超过 8 个字符 → 判定为封装；否则当前函数记为接口。
5. 判定为封装 → 不记录当前函数，按 3.8 入队 `data_chase`，目标为唯一业务下游，`fallback_handler` = 当前函数；`effective_outer` 取当前值，`origin_case_id` 取当前 case id，无条件处理时两者均为 null；把 `当前函数名(data)` 追加到 `evidence_chain`。
```

说明：

- 不再检查函数体是否简单、是否处理 data、是否写成员/全局。
- 纯校验/日志/框架转换函数在 3.6 的排除项阶段已经处理，不进入封装判定。
- data 下游包括纯校验调用；不再区分“业务调用”和“校验调用”。
- 名称比较忽略命名空间/类限定；完全相同也算封装。
- 名字不匹配、目标在路径外/scope 外、0 个目标、多个目标都保守地记录当前函数。

## 4. 3.9 第 2 步调整

3.9 处理 target_path 当前函数时，不再重复列出“真正处理/0 个/多个/名字不相近”等条件，改为引用 3.6 判定：

```text
2. 若当前函数定义在 `<target_path>` 下且是接收 data 的业务函数（非 dispatcher、非排除项）：按 3.6 的封装判定处理：
   - 封装 → 按 3.8 入队 `data_chase`，目标为唯一业务下游，`fallback_handler` = 当前函数，并把 `当前函数名(data)` 追加到 `evidence_chain`；结束当前工作项；
   - 唯一目标是 dispatcher/转发器 → 不记录当前函数；若已有 `fallback_handler`，按 3.9 现有 dispatcher 规则记录 fallback；否则按 3.8 入队 dispatch；
   - 其余（0 个/多个目标、目标在路径外或 scope 外、名字不匹配等）→ 按第 4 条记录当前函数，结束当前工作项。
```

## 5. 全局措辞

- 核心原则 3、第七章开头、约束 4、3.5、抗理性化、示例：把“明显封装/明显单线封装”改为“名字相近的单线封装”，把“真正处理 data”改为“按名字规则判定为非封装的第一层业务函数”，避免暗示仍在检查 data 处理语义。
- 术语“接口函数”改为：

```text
| 接口函数 | cmdId 用例分支中最终记录为外部接口的业务函数：位于 `<target_path>` 下并按名字规则判定为非封装，或找不到非封装业务函数时的最深封装函数 |
```

- `fallback_handler` 术语与 3.9 的 fallback evidence 标注中，“未找到真正处理函数”改为“未找到非封装业务函数”。
- 术语“封装函数”改为：

```text
| 封装函数 | target_path 内只有一个 data 下游目标，目标在 target_path/scope 内，且名称相同或前后缀扩展 ≤8 字符的函数 |
```

- `fallback_handler` 术语不变。

## 7. 预期效果

- 封装判定只依赖 data 下游目标、路径/scope 和名称，执行者不再需要判断函数体语义。
- 明显封装仍会下钻；不确定或复杂的函数保守地作为接口。
- fallback、路径外追踪、最终输出保持不变。
